# System Architecture

**Last updated:** 2026-09-08  
**Status:** Reflects current implemented system.

---

## Overview

CareerOS is a monorepo containing a Next.js web client and a NestJS API backed by PostgreSQL. The architecture is multi-tenant: every request, profile, job state, and application belongs to an `Organization` (workspace), enforced at the database and API layer.

```text
Next.js Web Client (apps/web)
    │  authenticated API calls
    ▼
NestJS API (apps/api)
    │  Prisma ORM
    ▼
PostgreSQL (Docker)

AI requests routed through:
    AiCapabilityService
        ├── Workspace BYOK credentials (byok_credentials table)
        ├── Platform env vars (OPENROUTER_API_KEY, OPENAI_API_KEY, ANTHROPIC_API_KEY)
        └── Honest unavailable state (no fabrication)

Job ingestion via:
    ApifyLinkedInAdapter
        └── APIFY_API_TOKEN (platform or per-request)
```

---

## Multi-Tenancy

The multi-tenant model is built on Better Auth's organization plugin.

- `Organization` is the workspace / tenant.
- `Member` is the relationship between a `User` and an `Organization`.
- `Session.activeOrganizationId` tracks the user's active workspace.
- All career data (`MasterCareerProfile`, `ResumeProfile`, `WorkspaceJobState`, `JobMatch`, `Application`, `ByokCredential`) is scoped to `organizationId`.

**Authorization rule:** Never assume that having an authenticated session means the user has an active organization. Always verify `activeOrganizationId` and membership before accessing workspace-scoped data.

---

## Authentication

CareerOS uses **Better Auth v1.4** for session and organization management.

- Sessions are database-backed (opaque session tokens, not JWT).
- Email/password authentication is implemented via Better Auth's credential provider.
- The global `BetterAuthGuard` validates every API request.
- The `WorkspaceMemberGuard` validates membership for workspace-scoped routes.

## Master Career Profile

The `MasterCareerProfile` is the single source of verified career truth per workspace.

- One per organization (`unique` constraint on `organizationId`).
- Contains: identity (name, headline, location, email), education, experience, projects, achievements, skills, technologies, certifications, publications, hackathons, links.
- Has an integer `version` field incremented on each save — used by the job matching system to detect stale match results.
- Never modified by AI features. AI Coach reads it as evidence and writes only to Resume Profiles.
- Client-submitted temporary IDs (e.g. `exp-1`, `skill-123`) are sanitized to `randomUUID()` before persistence.

## Resume Profiles

Resume Profiles are persistent, named resume configurations per career direction.

- Multiple per workspace (e.g. "SDE Resume", "Data Analyst Resume").
- Each profile maintains:
  - Section visibility and ordering
  - Priority record IDs (skills, experience, projects, achievements, certifications) — references into the Master Career Profile
  - Summary guidance
  - Highlight rules
  - Template ID
  - **LaTeX source** (stored in the `styleSettings` JSON field; auto-generated from a canonical template at creation)

### LaTeX Architecture

The canonical LaTeX template is generated by `latex-template.util.ts`. It is:
- A well-formed LaTeX article document using `geometry`, `enumitem`, `hyperref`, and custom `\resumesection{}` macros.
- Pre-populated with name, headline, skills, experience, projects, education, and certifications from the Master Career Profile.
- Stored per Resume Profile (not per version).
- Section content can be updated by the AI Coach's `applySectionRecommendation` method using regex replacement against the `\resumesection{...}` markers.

**Note:** CareerOS stores LaTeX source and generates it programmatically. It does not integrate an external LaTeX compiler (e.g. Overleaf, `pdflatex`). PDF compilation is not yet wired.

### Resume Versions

`ResumeVersion` records are audit snapshots attached to a `ResumeProfile`. They store:
- `masterProfileSnapshot` — a point-in-time copy of the Master Career Profile
- `selectedRecordIds` — the specific records included
- Job analysis evidence and match result
- Artifact metadata (jobId, source, creation context)

Applications reference `resumeProfileId` directly. A `ResumeVersion` is not required to apply to a job.

## Job Ingestion Pipeline

```text
POST /workspaces/:id/jobs/ingest
    ↓
JobIngestionService
    ↓
ApifyLinkedInAdapter.fetchJobs()
    ├── APIFY_API_TOKEN: params.apiKey ?? APIFY_API_TOKEN env var
    └── Calls: apify~linkedin-jobs-scraper actor (sync run)
    ↓
JobNormalizationService.normalize()
    └── Standardizes title, company, location, remote, skills, salary
    ↓
JobDeduplicationService.computeFingerprint()
    └── SHA-256 of normalized(company | title | location)
    ↓
PrismaJobsRepository.upsertCanonicalJob()
    └── Upsert by (source, externalId) or fingerprint
```

If `APIFY_API_TOKEN` is not configured, ingestion returns a clear error. No jobs are fabricated.

## Job Matching

Matching is deterministic — no AI required.

```text
JobMatchingService.match()
    Input: CanonicalJob + MasterCareerProfile + optional ResumeProfile + weights
    Output: overallScore, skillScore, roleScore, experienceScore, locationScore, seniorityScore,
            matchedSkills, missingSkills, confidence, explanation
```

- Scores are 0–1 floats; exposed as 0–100 integers to clients.
- `ensureJobMatches()` automatically runs matching for all listed jobs (bounded by `maxBatchSize`).
- Stale matches (where `profileVersion !== masterProfile.version`) are re-computed on next listing.

## Application Tracking

`Application` records are workspace-scoped and link to a canonical `Job`.

- Statuses: `saved | applied | screening | interview | offer | rejected | withdrawn`
- Status transitions are recorded in `ApplicationStatusHistory`
- Applications reference `resumeProfileId` directly (no `ResumeVersion` required)
- `resumeVersionId` is an optional secondary reference for audit purposes

## AI Capability Resolution

All AI features route through `AiCapabilityService.resolveCapability(workspaceId)`.

Priority order:
1. Workspace BYOK credential (`byok_credentials` table) — checked for: `openai`, `anthropic`, `google`, `mistral`
2. Platform environment: `OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`
3. **Unavailable** — returns `{ available: false, reason: '...' }` — never fabricates output

`generateCompletion()` supports:
- Anthropic: direct API call to `api.anthropic.com` (claude-3-5-haiku-20241022)
- OpenRouter: configurable base URL and model
- OpenAI and OpenAI-compatible: default `gpt-4o-mini`

Note: Google and Mistral BYOK keys are detected but currently routed through the OpenAI-compatible path. Provider-specific SDKs are not used — calls are direct HTTP.

## AI Coach

`AiCoachService` provides three endpoints:

| Endpoint | Description |
|---|---|
| `POST /workspaces/:id/ai-coach/analyze` | Role-level analysis grounded in Master Career Profile |
| `POST /workspaces/:id/ai-coach/section` | Section-level coaching (summary, experience, projects, skills, education) |
| `POST /workspaces/:id/ai-coach/apply-section` | Writes accepted recommendation to Resume Profile only |

Key rules enforced in code:
- Master Career Profile is never modified by AI Coach.
- All prompts include explicit evidence-grounding instructions ("Do NOT invent fake experience").
- When AI capability is unavailable, the endpoint returns `{ available: false, message: '...' }` — no placeholder advice.

## Insights

### AI Market Intelligence (`GET /workspaces/:id/insights/market`)

- Checks job data count first — returns unavailable if 0 jobs ingested.
- Checks AI capability — returns unavailable if not configured.
- When both are available: samples up to 20 ingested jobs, computes top required skills, sends real data to AI for synthesis.
- No hardcoded market statistics.

### Career Handbook (`GET /workspaces/:id/insights/handbook`)

- Fully offline, no AI or database required.
- Returns static educational reference for 7 fields: Software Engineering, Data Analysis, Product Management, Design, Research, Healthcare, Finance.
- Each field includes: description, common roles, core skills, technologies, keywords, learning path, study resources.

## Data Flow Diagram

```text
User submits onboarding form
    ↓
WorkspaceService.completeOnboarding()
    ├── Creates Organization + Member (if new)
    ├── Updates Session.activeOrganizationId
    ├── Creates MasterCareerProfile (seeded with name, headline, location, skills)
    └── Creates initial ResumeProfile (with canonical LaTeX auto-generated)

User updates career profile
    ↓
CareerProfileService.save()
    ├── Normalizes client IDs (exp-1 → UUID)
    └── Increments profile version

User views Job Radar
    ↓
JobsService.listByWorkspace()
    ├── Lists canonical jobs from DB
    ├── ensureJobMatches() — auto-matches stale/new jobs
    └── merges workspace job state (saved, dismissed, applied)

User applies to job
    ↓
JobsService.applyToJob()
    └── WorkspaceJobState.status = 'applied', records appliedAt, notes resumeProfileId

User requests AI Coach analysis
    ↓
AiCoachService.analyzeRole()
    ├── Loads Master Career Profile (evidence)
    ├── resolveCapability() → BYOK or platform or unavailable
    ├── If unavailable → returns honest message
    └── If available → grounds prompt in evidence → returns structured JSON
```
